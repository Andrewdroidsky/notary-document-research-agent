## Полная схема с описанием всех компонентов

## 1. ОБЗОР АРХИТЕКТУРЫ

### Принцип

Монолитный `notary_agent.py` (9171 строк) и `AGENTS.md` (375 строк) разбиваются на специализированные компоненты. Каждый компонент получает только тот контекст, который нужен для его задачи.

**Было:**
```
Пользователь → Python-скрипт → LLM (весь контекст сразу)
```

**Станет:**
```
Пользователь → Команда → Orchestrator → нужный Субагент
                                              ↓
                                    нужные Скиллы + Приказ
                                              ↓
                                            LLM
```

### Стек

- **LLM**: без изменений (вызов через Python → LLM API)
- **Оркестрация**: Python-скрипт (переработанный `notary_agent.py`)
- **Агенты/Скиллы**: `.md` файлы — системные промпты
- **Состояние**: `PROJECT_STATE.md` — живой индикатор
- **Хуки**: функции в Python-скрипте, вызываемые до/после LLM-вызовов

## 3. АГЕНТЫ (Agents)

### 3.1 ORCHESTRATOR

**Файл:** `agents/orchestrator.md`

**Роль:** Главный диспетчер. Не выполняет содержательную работу. Только читает состояние, принимает решения, маршрутизирует к субагентам.

**Preloaded skills:** нет (только AGENTS.md + PROJECT_STATE.md)

**Системный промпт:**
```
Ты — orchestrator нотариального агента.

Твоя единственная задача: прочитать состояние проекта и определить следующий шаг.

При каждом запуске:
1. Прочитай PROJECT_STATE.md — текущая тема, завершённые подтемы, следующая подтема.
2. Определи какой субагент нужен для следующего шага.
3. Сформируй минимальный контекст для этого субагента.
4. Передай управление.

Ты не ищешь документы. Ты не оформляешь карточки. Ты не пишешь тексты.
Ты только маршрутизируешь.

Доклад пользователю: одна строка — текущая тема, следующий шаг, ожидаемое действие.
```

**Что читает:**
- `AGENTS.md` — правила маршрутизации
- `PROJECT_STATE.md` — текущее состояние
- `Утверждаю.md` — при старте новой темы

**Что НЕ читает:** Мастер-Промпт, Приказы, скиллы поиска

---

### 3.2 OUTLINE-AGENT

**Файл:** `agents/outline-agent.md`

**Роль:** Анализирует список подтем новой темы, предлагает юридически обоснованное оглавление с возможным объединением подтем.

**Preloaded skills:**
- `legal-grouping.md` — критерии объединения подтем

**Системный промпт:**
```
Ты — юридический аналитик нотариального права.

Задача: получить список подтем новой темы и предложить оглавление.

Правила составления оглавления:
1. Подтемы НЕ дробятся механически — только по юридическому смыслу.
2. Две подтемы объединяются в одну, если:
   — требуют одинаковых нотариальных процедур;
   — регулируются одним нормативным блоком;
   — различаются только объектом, а не правовым режимом.
3. Итоговое число подтем в оглавлении может быть меньше исходного списка.
4. Каждая конечная подтема получает свой номер вида 19.1, 19.2 и т.д.

Формат ответа:
— Оглавление (предлагаемое)
— Обоснование объединений (если есть)
— Вопрос пользователю: утверждаете?

После утверждения пользователем — остановиться. Не рендерить приказы самостоятельно.
```

**Триггер:** команда `prepare-theme <N>` → draft-outline

**Результат:** предложенное оглавление → пользователь утверждает/корректирует

### 3.3 ORDER-RENDER-AGENT

**Файл:** `agents/order-render-agent.md`

**Роль:** После утверждения оглавления создаёт копии шаблона Приказа для каждой конечной подтемы. Создаёт папочную структуру.

**Preloaded skills:** нет (только шаблон Приказа)

**Системный промпт:**
```
Ты — технический агент рендеринга Приказов.

Задача: для каждой конечной подтемы из утверждённого Оглавления:
1. Взять шаблон Приказа.
2. Заменить в разделе III ОГЛАВЛЕНИЕ на конкретную подтему.
3. Заменить наименование подтемы во всех релевантных местах 11 Частей.
4. Сохранить как runs/theme-N/orders/<номер_подтемы>.md
5. Создать папку workspace: runs/theme-N/subtopics/<номер_подтемы>/

Остальной текст шаблона Приказа не изменять.
Имена файлов: короткий формат по номеру подтемы (19.1.md, 19.2.md).

После рендеринга всех Приказов:
— обновить PROJECT_STATE.md (приказы отрендерены: да)
— доложить пользователю: сколько Приказов создано, список подтем
— остановиться и ждать команды
```

**Триггер:** команда `approve-outline` → пользователь утвердил

**Результат:** файлы Приказов + папки workspace в `runs/theme-N/`

### 3.4 RESEARCH-AGENT

**Файл:** `agents/research-agent.md`

**Роль:** Основной исследовательский агент. Выполняет Части 2–5 для конкретной подтемы.

**Preloaded skills:**
- `search-spheres.md` — блоки I–XXXVII (карта сфер поиска)
- `fail-safe.md` — ANTI-OMIT, FAIL-SAFE, АО1–АО3
- `document-card.md` — формат карточки документа

**Получает через промпт (от orchestrator):**
- Название подтемы
- Приказ по данной подтеме (Части 2–5)
- НЕ получает: историю других подтем, другие Приказы

**Системный промпт:**
```
Ты — юридический аналитик-исследователь по нормативным актам РФ,
специализация — нотариальная деятельность.

У тебя preloaded:
- Карта сфер поиска (блоки I–XXXVII)
- Правила FAIL-SAFE и ANTI-OMIT
- Формат карточки документа

Задание получаешь через промпт: конкретная подтема + Приказ (Части 2–5).

Порядок работы:
1. Прочитай Приказ по данной подтеме.
2. Выполни Часть 2: Анализ области права.
3. Выполни Часть 3: Блоки сфер права I–XXXVII.
4. Выполни Часть 4: Поиск по органам власти.
5. Выполни Часть 5: Слойность.

Для каждого документа ОБЯЗАТЕЛЕН fetch-and-log до карточки.
[WEBFETCH-ДЕКЛАРАЦИЯ] в начале каждой Части.
[WEBFETCH-ПОДТВЕРЖДЕНИЕ] в конце каждой Части.

Ты работаешь только по своей подтеме. Ты не знаешь о других подтемах.
Работай в режиме silent end-to-end: один прогон, без промежуточных сообщений.
```

**Хуки:**
- `PreToolUse` → проверяет наличие fetch-and-log перед карточкой
- `PostToolUse` → логирует результат fetch в research-log

**Результат:** Части 2–5 в stage-outputs → capture-part-output

### 3.5 DELTA-AGENT

**Файл:** `agents/delta-agent.md`

**Роль:** Выполняет Части 6–9. Получает корпус документов из Частей 2–5 и расширяет его.

**Preloaded skills:**
- `url-verification.md` — правила URL1/URL2/VERIFIED/Карантин
- `fail-safe.md` — ANTI-OMIT, АО1–АО3
- `document-card.md` — формат карточки

**Получает через промпт:**
- Название подтемы
- Корпус документов из Частей 2–5 (только список, не полные карточки)
- Приказ (Части 6–9)
- НЕ получает: всю историю, другие подтемы

**Системный промпт:**
```
Ты — аудитор и расширитель документного корпуса по нотариальным темам РФ.

У тебя preloaded:
- Правила URL1/URL2/VERIFIED/Карантин
- Правила FAIL-SAFE и ANTI-OMIT
- Формат карточки документа

Задание: получаешь уже найденный корпус документов (Части 2–5) и Приказ (Части 6–9).

Порядок работы:
1. Выполни Часть 6: Фильтр + ОБЯЗАТЕЛЬНЫЙ новый web-поиск по теме.
2. Выполни Часть 7: Новые документы без повторений.
3. Выполни Часть 8: Федеральный delta-check.
4. Выполни Часть 9: Дельта-аудит.

КРИТИЧНО:
— Части 6–9 НЕ являются пересмотром уже найденного.
— Каждая Часть требует нового web-поиска по каскаду источников (1→7).
— "Новых документов не выявлено" допустимо только после реального нового прохода.
— Повтор уже выданных документов запрещён.

Silent end-to-end: один прогон, без промежуточных сообщений в чат.
```

**Хуки:**
- `PreToolUse` → проверяет новый web-поиск перед каждой Частью 6–9
- `PostToolUse` → логирует новые документы

**Результат:** Части 6–9 в stage-outputs → capture-part-output

### 3.6 ASSEMBLY-AGENT

**Файл:** `agents/assembly-agent.md`

**Роль:** Выполняет Части 10–11. Собирает финальный `.md` из всех захваченных Частей.

**Preloaded skills:**
- `metric-gate.md` — пороги качества

**Получает через промпт:**
- Название подтемы
- Приказ (Части 10–11)
- Путь к stage-outputs (агент читает уже захваченные Части)

**Системный промпт:**
```
Ты — финальный сборщик нотариального документа.

У тебя preloaded:
- Критерии качества (слова, знаки, URL, page count)

Задача в два этапа:

ЭТАП 1: Части 10–11
1. Прочитай захваченные Части 2–9.
2. На их основе выполни Часть 10: Расширенный мини-конспект.
   — не пересказ, а опорный учебно-практический конспект
   — 10–12 пунктов с документами-опорами после каждого
3. Выполни Часть 11: Перечень практических заданий.
   — только 4-я колонка дневника
   — только выполненные стажером действия
   — без документов, без мини-конспекта

ЭТАП 2: Сборка финального .md
1. Собери все Части 2–11 в один документ.
2. Разделители: ЧАСТЬ 2, ЧАСТЬ 3 ... ЧАСТЬ 11.
3. Служебные Части I-III — не публиковать.
4. Проверь метрики: слова, знаки, URL1, URL2.
5. Если метрики не достигнуты — сообщи orchestrator'у о недоборе.

Не изменяй уже захваченные Части — только собирай.
```

**Хук:**
- `PostToolUse` → автоматический metric-check после сборки

**Результат:** финальный `.md` → передаётся в quality-agent

### 3.7 QUALITY-AGENT (PRE-PUBLISH GATE)

**Файл:** `agents/quality-agent.md`

**Роль:** Финальная проверка перед публикацией. Пользователь не должен быть первым валидатором дефектов.

**Preloaded skills:**
- `metric-gate.md` — пороги качества
- `document-card.md` — эталон формата карточки

**Системный промпт:**
```
Ты — валидатор качества нотариального документа.

Задача: проверить финальный .md перед публикацией по чеклисту.

ЧЕКЛИСТ (все пункты обязательны):
1. Все Части 2–11 присутствуют с правильными разделителями.
2. Части 3, 4, 5 — все документы оформлены карточками.
3. Каждая карточка содержит:
   — полное наименование
   — структурный элемент
   — URL1
   — URL2 (или КАРАНТИН с протоколом)
   — VERIFIED URL2: ДА/НЕТ
   — Заголовок страницы URL2
   — Сверка реквизитов
4. Часть 10 — после каждого пункта есть документы-опоры.
5. Часть 11 — нет документов, только действия стажера.
6. Метрики: слова ≥ 8000, знаки ≥ 122000, URL2 ≥ 35.
7. Имя файла соответствует краткому заголовку из Оглавления.

Если ВСЕ пункты пройдены → PASS → сообщить orchestrator'у: готово к публикации.
Если ХОТЯ БЫ ОДИН не пройден → FAIL → указать конкретный дефект и вернуть
в соответствующий агент (research-agent или assembly-agent).

Не публиковать самостоятельно. Только проверять и докладывать.
```

**Результат:** PASS → `/publish` | FAIL → возврат с указанием дефекта

## 4. СКИЛЛЫ (Skills)

Скиллы — это `.md` файлы с переиспользуемым знанием. Python-скрипт загружает нужные скиллы и добавляет их к системному промпту агента перед отправкой в LLM.

---

### 4.1 search-spheres.md

**Содержит:** Блоки I–XXXVII из Мастер-Промпта (карта сфер права).

**Размер:** ~300 строк

**Загружается:** research-agent

**Что даёт агенту:** полную карту всех юридических сфер, которые нужно проверить по каждой теме. От конституционного до энергетического права. Агент знает — нельзя ограничиться 1–2 "главными" актами.

**Структура:**
```
# Карта сфер поиска

## Обязательный алгоритм
[3 шага декомпозиции темы]

## Блоки I–XXXVII
I.   Базовые отрасли материального права
II.  Процессуальное право (ОБЯЗАТЕЛЬНО)
III. Налоговое право (ОБЯЗАТЕЛЬНО)
...
XXXVII. Энергетическое право

## Дополнительный охват (раздел 3.1)
[18 контрольных органов с отметками НАЙДЕНО/НЕ ВЫЯВЛЕНО/НЕПРИМЕНИМО]
```

---

### 4.2 url-verification.md

**Содержит:** Правила верификации URL1/URL2, VERIFIED, Карантин, каскад источников.

**Размер:** ~150 строк

**Загружается:** research-agent, delta-agent

**Что даёт агенту:** точный протокол проверки каждой ссылки. Агент знает — нельзя писать карточку без предшествующего fetch. VERIFIED URL2: ДА только после реального открытия страницы.

**Структура:**
```
# Протокол верификации ссылок

## Каскад источников (1→8)
[список с URL]

## Цикл URL2-верификации
[ПОИСК → ОТКРЫТИЕ → СВЕРКА → VERIFIED]

## Двухуровневое правило URL2
Уровень 1: структурный элемент
Уровень 2: документ/карточка (fallback)

## Карантин
[условия применения]

## АО1–АО3 (анти-отказ)
[правила дожима верификации]
```

```
9. Сверка реквизитов:

[в code-блоке:]
URL1: ...
URL2: ... / отсутствует (КАРАНТИН)
```

### 4.4 fail-safe.md

**Содержит:** FAIL-SAFE правило, ANTI-OMIT (контроль полноты по слоям), правила Карантина, АО1–АО3.

```
# FAIL-SAFE и контроль полноты

## FAIL-SAFE правило
[если документов нет — писать явно]

Слой 1: Кодифицированные источники
Слой 2: Специальное нотариальное регулирование
Слой 3: Процессуальный/контрольный слой
Слой 4: Подзаконные акты федеральных органов
Слой 5: Акты ФНП
Слой 6: Пленум ВС РФ

## АО1–АО3 (анти-отказ)
[запрет останавливаться до исчерпания всех веб-инструментов]

## Проверка слепых зон
[2–5 потенциально упущенных факторов перед финалом]
```

### 4.5 metric-gate.md

**Содержит:** Числовые пороги качества финального документа.

**Размер:** ~30 строк

**Загружается:** assembly-agent, quality-agent

## 5. КОМАНДЫ (Commands)

Все команды — вызовы Python-скрипта из терминала.

```bash
# Старт новой темы
python notary_agent.py prepare-theme 19
# → orchestrator читает Утверждаю.md
# → запускает outline-agent

# После изучения оглавления пользователем
python notary_agent.py approve-outline 19
# → сохраняет утверждённое оглавление в runs/theme-19/outline.md
# → запускает order-render-agent

# Запуск подтемы
python notary_agent.py run-subtopic 19.3
# → orchestrator читает PROJECT_STATE.md
# → запускает research-agent с Приказом 19.3 + скиллами

# Захват части (после выдачи LLM)
python notary_agent.py capture-part 19.3 2
# → сохраняет вывод в stage-outputs
# → помечает доверенной/недоверенной (UNTRUSTED если без fetch-and-log)

# Запуск delta-агента
python notary_agent.py run-delta 19.3
# → orchestrator передаёт корпус Частей 2–5 + Приказ (Части 6–9)
# → запускает delta-agent

# Сборка финала
python notary_agent.py assemble 19.3
# → запускает assembly-agent

# Проверка метрик
python notary_agent.py metric-check 19.3
# → локальный подсчёт без LLM-вызова

# Публикация
python notary_agent.py publish 19.3
# → quality-agent → при PASS → копирует в 04-output

# Переход к следующей теме
python notary_agent.py next-theme
# → orchestrator обновляет PROJECT_STATE.md
# → готов к prepare-theme 20
```

## 6. ХУКИ (Hooks)

Хуки — функции в Python-скрипте, вызываемые автоматически до/после LLM-вызовов. Не тратят токены агента.

```
PreToolUse (перед отправкой в LLM)
│
├── Проверяет: если это research-agent или delta-agent
│   и текущая часть 2–9 → проверить наличие fetch-and-log
│   в предыдущем выводе перед каждой карточкой
│
├── Если fetch-and-log отсутствует → помечает как UNTRUSTED
│   → capture-part заблокирует захват
│
└── Логирует: время запуска, агент, подтема, часть

PostToolUse (после получения ответа от LLM)
│
├── Автоматически обновляет run-manifest.json
│   (какие части захвачены, метрики)
│
├── Логирует: время завершения, количество токенов
│
└── При сборке финала → автоматический metric-check

PostToolUseFailure (при ошибке LLM или fetch)
│
├── Логирует ошибку с деталями
│
├── НЕ прерывает прогон
│
└── Помечает часть как требующую повтора

Stop (при завершении подтемы)
│
├── Обновляет PROJECT_STATE.md:
│   — подтема N завершена: да
│   — дата завершения
│   — метрики (слова, знаки, URL1, URL2, pages)
│   — следующая подтема: N+1
│
└── Проверяет: все подтемы темы завершены?
    Если да → тема закрыта → готов к next-theme
```

## 11. ЧТО МЕНЯЕТСЯ В notary_agent.py

### Убрать:
- Весь текст промптов из кода (перенести в agents/*.md и skills/*.md)
- Дублирующиеся константы промптов (WEBFETCH_MANDATE, FOLLOWUP_SEARCH_MANDATE и др.)
- Хардкод путей (→ в config.json)

### Добавить:
- `load_agent(name)` — загружает agents/<name>.md
- `load_skills(names)` — загружает список skills/*.md и склеивает
- `build_context(agent, skills, order, extra)` — собирает полный контекст для LLM
- `run_hook(event, context)` — вызывает нужный хук
- Новые команды: `prepare-theme`, `approve-outline`, `run-delta`, `next-theme`

### Сохранить без изменений:
- `fetch_and_log` — работает хорошо
- `capture_part_output` — логика capture
- `assemble_subtopic_final` — сборка .md
- `metric_check` — подсчёт метрик
- `build_docx` — генерация .docx
- `validate_part_output` — валидация
