## Раздел 3. Команды Кодекс-агента

### Основные команды

| Команда | Когда | Что делает |
|---------|-------|-----------|
| `run-subtopic 16.8.2` | Старт подтемы | Создаёт workspace, проверяет Приказ, готовит папки |
| `execute-part-01 16.8.2` | После старта | Выполняет Часть 1 (подтверждение правил, "ЖДУ GO") |
| `prepare-part-02-web 16.8.2` | Перед Частью 2 | Готовит план веб-поиска |
| `capture-part-output 16.8.2 2` | После LLM выдал Часть 2 | Валидирует и захватывает Часть в run |
| `capture-part-output 16.8.2 2 --source-file tmp/part-02.md` | Если записано в файл | То же, но читает из файла |
| `assemble-subtopic-final 16.8.2` | После всех Частей | Собирает финал, проверяет метрики |
| `assemble-subtopic-final 16.8.2 --publish` | Готов к публикации | Публикует + обновляет PROJECT_STATE.md |
| `metric-check 16.8.2` | В любой момент | Показывает текущие метрики без токенов |

### Как давать команды Кодексу

**Формула:** Что + По какой подтеме + Критерий готовности + Покажи результат.

**Примеры хороших команд:**
> Запусти `run-subtopic 16.8.2`. Покажи что создано в папке.

> Выполни Части 3, 4, 5 по 16.8.2. После каждого capture покажи статус валидации из manifest.json.

> После всех Частей — `assemble-subtopic-final 16.8.2`. Покажи pre-publish JSON до публикации. Если все пороги достигнуты — публикуй.

> Прочитай `16.md` и скажи какая подтема следует после 16.8.2 по порядку.

**Чего НЕ говорить:**
- "Сделай всё" — слишком широко
- "Постарайся не ошибиться" — не задача
- Принимать "готово" без метрик или diff — нет доказательства

## Раздел 4. Полный workflow по подтеме — шаг за шагом

### Шаг 0 — Подготовка
Кодекс поднимает папку run, проверяет Приказ для данной подтемы, очищает старые артефакты.

**Что проверить:** файл `02-orders/16.8.2.md` существует и содержит правильное Оглавление.

### Шаг 1 — Часть 1 (автоматически)
Подтверждение правил. Финальная строка: `ЖДУ СИГНАЛ GO/СТАРТ`. Поиск не начался.

### Шаг 2 — Часть 2 (главный поисковый блок)
Строит: `АНАЛИЗ ОБЛАСТИ ПРАВА` → `КОДЕКСЫ И БАЗОВЫЕ АКТЫ` → `A. РЕГУЛЯТОРНОЕ ЯДРО` → `B. ОПОРНЫЕ ДОКУМЕНТЫ` → `КАРАНТИН` → `FAIL-SAFE CHECK`.

Записывается порционно в tmp-файл, затем одной командой захватывается. Сразу валидируется.

### Шаги 3–5 — Части 3, 4, 5

**Часть 3:** 37 блоков I–XXXVII (сферы права). Каждый применимый блок — документы + URL2. Неприменимый — "не применяется".

**Часть 4:** ДОПОЛНИТЕЛЬНЫЙ АЛГОРИТМ ОХВАТА (18 подпунктов): органы, суды, цифровой слой, международный.

**Часть 5:** СЛОЙНОСТЬ (6 слоёв).

Каждая Часть — отдельный capture с валидацией.

### Шаги 6–9 — Части 6–9 (follow-up)

- Часть 6: поиск по органам власти (Минюст, ФНП, ЦБ, суды)
- Часть 7: дельта-аудит (что пропустили)
- Часть 8: цифровой и специальный субъектный слой
- Часть 9: международный и процессуальный слой

**Правило:** слабый результат если нет новых документов. Обязателен новый веб-поиск. "Новых документов не выявлено" без поиска — FAIL.

Follow-up пакет содержит только список уже найденных документов (строки `Полное наименование:`), не полный текст.

### Шаг 10 — Часть 10 (мини-конспект)
Развёрнутый конспект ключевых правовых положений. После каждого пункта — документы-опоры с URL2.

### Шаг 11 — Часть 11 (дневник стажёра)
Только 4-я колонка: что делал стажёр. Без перечисления документов.

### Шаг 12 — Финальная сборка
```
assemble-subtopic-final 16.8.2 --publish
```
Агент: склеивает Части 2–11 → gate по метрикам → если OK → публикует `.md` и `.docx` → обновляет PROJECT_STATE.md с правильной следующей подтемой из `16.md`.

## Раздел 6. Валидация — что проверяется на каждой Части

| Часть | Что проверяет валидатор |
|-------|------------------------|
| 1 | Наличие строки `ЖДУ СИГНАЛ GO` |
| 2 | Обязательные блоки (РЕГУЛЯТОРНОЕ ЯДРО, ОПОРНЫЕ ДОКУМЕНТЫ, КАРАНТИН, FAIL-SAFE CHECK), URL1 в карточках |
| 3 | Все 37 блоков I–XXXVII присутствуют; применимые блоки содержат URL2 |
| 4 | Минимум 3 строки `Статус:`, URL2 count ≥ count `Статус:` |
| 5 | Есть хотя бы один `Статус:`, URL2 count > 0 |
| 6–9 | Все 6 полей карточки (`Вид документа`, `Полное наименование`, `Структурный элемент`, `URL1`, `URL2`, `Статус верификации`); нет перезапуска с `ТЕМА:`; нет `Прямой документ(ы):` |
| 10 | Каждый нумерованный пункт содержит URL2 |
| 11 | Минимум 15 пунктов, максимум 20; нет ссылок на документы |

**Правило URL2 в карточке:** URL2 должен стоять внутри блока карточки, не в конце раздела. Если URL2 есть только в конце — FAIL.

## Раздел 10. Уровни 1 и 2 защиты от галлюцинации — реализация в Claude-версии (07.04.2026)

### Контекст

В ходе анализа системной галлюцинации Qwen Code (07.04.2026) разработаны четыре уровня структурного изменения поведения агентов. В Claude-версию `notary_agent.py` внесены Уровни 1 и 2. Уровень 3 (grounded research session) не нужен — Claude имеет нативный `WebSearch` в диалоге. Уровень 4 (API-driven interleaved) признан нецелесообразным для CLI-воркфлоу.

Полный анализ механики галлюцинации и все четыре уровня — см. `Architecture Control — Qwen.md`, Раздел 10.

---

### Уровень 1 — Новые пороги URL (реализовано в `notary_agent.py`)

**Было:**
```python
PUBLISH_MIN_URL1 = 80  # жёсткий блокер
PUBLISH_MIN_URL2 = 80  # жёсткий блокер
```

**Стало:**
```python
# URL1 — только advisory
PUBLISH_TARGET_URL1 = 80
PUBLISH_MIN_URL1 = PUBLISH_TARGET_URL1  # alias

# URL2 — два отдельных порога
PUBLISH_MIN_URL2 = 35      # жёсткий floor (блокирует публикацию)
PUBLISH_TARGET_URL2 = 50   # advisory goal (предупреждение выше floor)
```

**Добавлена функция `collect_publish_metric_advisories()`** — печатает предупреждения, не блокирует. Вызывается из `enforce_publish_metric_floor()` после прохождения жёстких проверок.

**`collect_publish_metric_shortfalls()`** — больше не блокирует по URL1. Блокирует только по words, chars, и URL2 < 35.

---

### Уровень 2 — Commitment protocol (реализовано в `notary_agent.py`)

**Добавлен `SEARCH_DECLARATION_RE`** — регулярное выражение, распознающее маркеры реального поиска в тексте Части:
- `>>> ПОИСК:` / `>>> SEARCH:`
- `[ПОИСК #N]`
- `WEB_SEARCH:` / `web_search(`
- `Запрос #N:`

**Добавлена `check_search_grounding(content, part_number)`** — для Частей 2–9 проверяет соотношение карточек к маркерам поиска:
- 0 маркеров при ≥10 карточках → предупреждение
- Ratio >20 карточек на 1 маркер → предупреждение
- Advisory только, не блокирует

**Вызов добавлен в `cmd_capture_part_output()`** сразу после нормализации контента. Для Claude Code workflow (реальные WebSearch tool calls без inline-маркеров) предупреждений не будет — ratio = 0 markers, но card_count < 5 threshold или нет 10+ карточек подряд без маркера.
