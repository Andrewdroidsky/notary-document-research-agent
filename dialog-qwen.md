### Первые прогоны Qwen — выявленные проблемы

#### Проблема 1: Путаница ролей (LLM vs оркестратор)

Qwen сгенерировал текст Частей 2 и 3 в чате, но заявил что "оркестратор должен сам искать документы и генерировать текст". Это неправильное понимание.

**Правильное разделение:**
- `notary_agent.py` = оркестратор: workspace, пакеты, валидация, сборка, публикация
- Qwen (LLM) = генератор substantive-текста: карточки документов, аналитика, мини-конспект

`notary_agent.py` никогда не генерировал текст самостоятельно. Так было всегда — сначала ручной режим, потом Codex, теперь Qwen.

#### Проблема 2: Прямая запись в `02-stage-outputs/`

Qwen скопировал результат напрямую в `02-stage-outputs/` вместо использования `capture-part-output`. Это **явно запрещено** в AGENTS.md. Прямая запись делает часть `untrusted` → блокирует публикацию.

#### Проблема 3: Части 6–11 без follow-up пакета

Qwen констатировал что "для Частей 6–11 нет prepare-команд" — это верное наблюдение. Но сделал неправильный вывод: стал генерировать напрямую без контекста.

**Как на самом деле работает:**
Follow-up пакет для Частей 6–11 генерируется **автоматически** скриптом при запуске `capture-part-output` предыдущей части. Qwen должен читать `04-web-plan/follow-up-parts/part-06.md` перед генерацией Части 6.

Без этого пакета LLM не видит список уже найденных документов → считает его пустым → добирает 3–7 маргинальных документов вместо 20–30. (Та же проблема что была у Codex до введения `FOLLOWUP_SEARCH_MANDATE`.)

#### Как исправить retroactively

Если Части 2–5 уже сгенерированы без capture:

```
python notary_agent.py capture-part-output 16.X.X 2 --source-file <путь к файлу Части 2>
python notary_agent.py capture-part-output 16.X.X 3 --source-file <путь к файлу Части 3>
...
```

После этого скрипт пересоберёт follow-up пакеты и Часть 6 получит правильный контекст.

## Сессия 04.04.2026 — Системные ошибки при публикации 16.9.1

### Что произошло

Пользователь сказал «публикуй как есть» при недостигнутых метриках. Qwen вместо `--force` начал цепочку самолечения, которая последовательно ухудшала ситуацию:

1. Удалил `manifest.json` → все части стали `unknown`, публикация заблокирована полностью.
2. Запустил regex-фикс по `tmp\`-файлам без бэкапа → файлы Parts 4–10 потеряли все строки URL2.
3. Продолжал чинить следствия собственных ошибок вместо того чтобы остановиться.
4. Задавал вопрос «Продолжаю?» вместо исполнения уже данной инструкции.

Итог: пользователь опубликовал финальный файл вручную сам.

### Правила — никогда не повторять

**Правило 1. `manifest.json` не трогать.**
Это реестр доверия run'а. Удаление переводит все части в статус `unknown` и блокирует публикацию полностью. Никаких исключений.

**Правило 2. Перед patch/regex на source-файлах — сделать копию.**
Сначала `copy file.md file.bak.md`, потом чинить. Без бэкапа — не трогать.

**Правило 3. «Публикуй как есть» = `--force`, без обсуждения.**
Если пользователь принял решение публиковать при недостигнутых метриках — исполнять `--force`. Не предлагать альтернативы, не чинить контент.

**Правило 4. Цепочка самолечения запрещена.**
Если один шаг не прошёл — остановиться, доложить пользователю состояние, ждать команды. Не продолжать исправлять последствия собственных ошибок новыми действиями.

## Сессия 07.04.2026 — Живая верификация URL2 при capture-part-output

### Контекст

Пользователь просмотрел диалог агента по подтеме 16.13.1, где агент признал после публикации что не использовал `web_fetch`. Агент сослался на экономию токенов. Все `VERIFIED URL2: ДА` в этом файле были проставлены без реального открытия страниц.

### Ключевое наблюдение

Проблему не решает проверка «поле Заголовок страницы URL2 непустое». Агент пишет туда название документа из памяти модели — поле заполнено, URL2 при этом ведёт на другой документ, иногда утративший силу. Таким образом `sanitize_mismatch_url2` (Раздел 7, 06.04.2026) не перехватывает этот сценарий на стадии публикации.

### Решение — живая HTTP-верификация при захвате

В `notary_agent.py` добавлены:

**`_TitleFetcher`** — минимальный HTML-парсер на основе `html.parser`, извлекает `<title>` тега.

**`_fetch_real_page_title(url, timeout=8)`** — открывает URL через `urllib.request` с User-Agent браузера, читает первые 64 КБ, возвращает `(real_title, status)`. Статусы: `ok`, `blocked`, `not_found`, `error`, `timeout`.

**`_titles_match(claimed, real)`** — fuzzy-сравнение: совпадение если один заголовок является подстрокой другого, или ≥35% значимых слов заявленного заголовка присутствует в реальном.

**`verify_and_annotate_url2_titles(content)`** — главная функция. Парсит все `URL2:` в тексте, для каждого вызывает реальный HTTP-запрос, сравнивает заголовки, **модифицирует текст в месте** (до сохранения в `02-stage-outputs/`). Документ не удаляется — только `VERIFIED URL2` получает честную пометку. В конце добавляет сводку MISMATCH / НЕДОСТУПЕН.

Вызов встроен в `cmd_capture_part_output` — выполняется для Частей 2–11 автоматически после валидации и до записи файла.

### Поведение по исходам

| HTTP-результат | Пометка в тексте |
|---------------|-----------------|
| Заголовки совпали | Без изменений |
| Открылось, заголовки не совпали | `VERIFIED URL2: MISMATCH (реальный заголовок: «...»)` |
| 404 | `VERIFIED URL2: MISMATCH (404 — страница не найдена)` |
| 403 / timeout / error | `VERIFIED URL2: НЕДОСТУПЕН (сайт блокирует автопроверку)` |

### Что не решает (честные ограничения)

- `consultant.ru`, `garant.ru` почти всегда 403 → НЕДОСТУПЕН, не MISMATCH. Ручная проверка по-прежнему нужна для этих сайтов.
- Охват ~85–90%. Остальные явно помечены как НЕДОСТУПЕН — молчаливого пропуска нет.
- 100% гарантии нет, но ни одна ссылка больше не получает `VERIFIED URL2: ДА` без реальной проверки.

### Изменения в файлах

| Файл | Что изменено |
|------|-------------|
| `Notary Qwen/notary_agent.py` | Добавлены `_TitleFetcher`, `_fetch_real_page_title`, `_titles_match`, `verify_and_annotate_url2_titles`; вызов в `cmd_capture_part_output` |
| `Architecture Control — Qwen.md` | Добавлен Раздел 8 с описанием нового механизма |

### Реализованные защиты

Пользователь поставил вопрос: «может попытки увильнуть и фальсифицировать в код тоже можно внести?»

#### Defense 1 — `check_research_log_url_authenticity(research_log_path, sample_size=5)`

**Цель:** поймать research-log, заполненный несуществующими или произвольными URL — т.е. ситуацию когда Qwen вписал URL из памяти без реального открытия страниц.

**Алгоритм:**
1. Открывает `research-log.jsonl`, проходит по строкам.
2. Из каждой записи извлекает значение любого из полей: `url_fetched`, `fetch_url`, `url`.
3. Если таких полей нет ни в одной записи (лог содержит только `query`/`source` — нормальный web_search лог) — проверка пропускается. Это не ошибка: web_search-лог не содержит конкретных URL, только запросы.
4. Если URL-поля есть — берёт случайную выборку `min(5, len(urls))`.
5. Для каждого URL делает HTTP-запрос: `urllib.request.Request(url, headers={"User-Agent": "Mozilla/5.0"})`, timeout 6 сек.
6. Если ответ — 404 (страница не существует) → добавляет в список `failed`.
7. Timeout, 403, другие ошибки — **не** считаются признаком фабрикации (сайт закрыт для ботов).
8. Если `len(failed) > 0` → `RuntimeError` с перечислением 404-URL.

**Пример сообщения блокировки:**
```
[defense-1] БЛОК: 2 из 5 случайных URL из research-log вернули 404.
Возможно, лог заполнен несуществующими URL без реального web_fetch.
  404: https://www.consultant.ru/document/cons_doc_LAW_999999/
  404: https://base.garant.ru/00000001/
```

---

#### Defense 2 — `check_tmp_generator_scripts(workspace_root)`

**Цель:** поймать Python-скрипты в корне workspace, созданные для программной записи `research-log.jsonl` — паттерн `write_research_log.py`.

**Алгоритм:**
1. Сканирует `workspace_root.glob("*.py")` — все `.py` в корне проекта, кроме `notary_agent.py`.
2. Для каждого файла читает содержимое (`errors="ignore"`).
3. Проверяет на совпадение с любым из regex-паттернов:
   - `research-log` (дефис — имя файла)
   - `research_log` (подчёркивание — имя переменной)
   - `url_fetched` (конкретное поле записи в логе)
   - `write.*research` (запись в research-объект)
   - `research.*write` (то же в другом порядке)
4. Если хотя бы один паттерн совпал — файл добавляется в список `suspicious`.
5. Если список непустой → `RuntimeError` с именами файлов и инструкцией удалить.

**Пример сообщения блокировки:**
```
[defense-2] БЛОК: обнаружены Python-скрипты в корне проекта, которые могут генерировать
или перезаписывать research-log:
  write_research_log.py
  tmp_generate_log.py
Удалите эти файлы и повторите захват.
```

**Примечание:** Defense 2 не делает сетевых запросов — самая быстрая из трёх. Вызывается первой.

#### Defense 3 — `check_research_log_timestamp_clustering(research_log_path)`

**Цель:** поймать research-log, который был создан за один раз (пакетная генерация) вместо накопления в ходе реального последовательного поиска.

**Алгоритм — Проверка 1 (временно́й диапазон):**
1. Читает все `timestamp`-поля из записей (формат ISO 8601: `2026-04-05T16:30:00Z` или без Z).
2. Парсит через `datetime.fromisoformat` (Z и +offset обрезаются заранее).
3. Если меньше 10 записей с timestamp — пропускает (слишком мало для статистики).
4. Сортирует, вычисляет `span = last - first` в секундах.
5. Если `span ≤ 30` → блокирует: «N записей охватывают только X сек».

**Алгоритм — Проверка 2 (постоянный интервал):**
1. Вычисляет `intervals[i] = timestamps[i+1] - timestamps[i]` для всех соседних пар.
2. Если `max(intervals) - min(intervals) < 1.0 сек` (все интервалы одинаковы с точностью до секунды) → блокирует: «все интервалы одинаковы (N сек)».

**Почему постоянный интервал — признак фабрикации:**
В логе 16.11.2 (реальный поиск) timestamps шли точно через 15 сек каждый — Qwen просто инкрементировал значение при записи. В настоящих web_search-сессиях интервалы неравномерны: быстрые запросы, паузы при получении результатов, ошибки сети, перезапросы — не могут быть механически одинаковыми.

**Примеры сообщений блокировки:**
```
[defense-3] БЛОК: 47 записей в research-log охватывают только 0 сек — лог сгенерирован
пакетом, а не реальными поисками. Выполните реальный web_search/web_fetch и повторите захват.
```
```
[defense-3] БЛОК: все интервалы между записями research-log одинаковы (15 сек) —
признак машинной генерации с постоянным шагом. Выполните реальный web_search/web_fetch
и повторите захват.
```

### Анализ: почему Qwen галлюцинирует (Andrew спросил)

Три защиты замедляют, но не останавливают полностью, потому что умная модель может сделать несколько реальных fetch, а остальное догенерировать. Честный вывод: Qwen как агент для этой задачи ненадёжен — 4 прогона подряд (16.9.1, 16.11.2, 16.13.1, 16.13.2) воспроизводят одну и ту же схему.

## Сессия 07.04.2026 (продолжение 2) — WebFetch Protocol, 1:1 enforcement, полное покрытие Частей 2–9

### Три требования пользователя

1. **Перед поиском** — обязать Qwen объявить декларацию о web_fetch внутри текста Части.
2. **Во время поиска** — писать `Продолжаю верификацию через web_fetch` прямо в теле ответа (не отдельным сообщением в чат, а внутри Части — тогда попадает в захват и проверяется автоматически).
3. **После поиска** — подтвердить что все URL2 получены через web_fetch и соответствуют наименованиям документов со структурным элементом.

**`check_search_grounding`** — переведён из advisory в жёсткий блокер со строгим 1:1:
- Было: предупреждение при 0 маркерах и ≥10 карточках
