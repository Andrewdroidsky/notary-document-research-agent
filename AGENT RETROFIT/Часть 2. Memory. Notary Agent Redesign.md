# Часть 2. Memory. Notary Agent Redesign

## Контекст проекта
- **Проект:** `C:\Users\koper\OneDrive\Documents\New project` — нотариальный агент
- **Задача:** 154 юридических темы по нотариальной стажировке, декабрь 2025 — декабрь 2026
- **Стек:** Python-скрипт (`notary_agent.py`) → OpenAI API (функция `call_openai`)
- **НЕ использует:** Claude Code, Claude API — только Python + внешний LLM

**Why:** Пользователь изучил agents engineering и хочет применить принципы к своему проекту. Существующая система работает, цель — не сломать, а правильно переархитектурировать.
**How to apply:** LLM вызывается через Python, а не через Claude Code. "Агенты", "скиллы", "хуки" — это концепции, реализованные в Python-скрипте и .md файлах, не нативные Claude Code сущности.

## Ключевые инсайты сессии

### Vibe coding vs. Agents Engineering
Текущий `notary_agent.py` (9171 строк) — vibe coding: монолит, весь контекст всегда в LLM, дублирование промптов (АО1–АО3 встречаются дважды), хардкод путей, AGENTS.md на 375 строк.

Целевое состояние: каждый агент получает только нужный ему контекст. Уменьшение с ~2000+ строк контекста на вызов до 100–500 строк.

### Структура архитектуры
**7 агентов** (системные промпты в `.md` файлах):
- `orchestrator` — диспетчер, читает PROJECT_STATE.md, маршрутизирует
- `outline-agent` — анализирует список подтем, предлагает оглавление с объединениями
- `order-render-agent` — рендерит Приказы по шаблону для каждой подтемы
- `research-agent` — Части 2–5 (основной поиск), preloaded: search-spheres + fail-safe + document-card
- `delta-agent` — Части 6–9 (расширение корпуса), preloaded: url-verification + fail-safe + document-card
- `assembly-agent` — Части 10–11 + финальная сборка .md, preloaded: metric-gate
- `quality-agent` — PRE-PUBLISH GATE, checklist 15+ пунктов, PASS/FAIL

**6 скиллов** (декомпозиция из Мастер-Промпта 713 строк → 5 файлов):
- `search-spheres.md` (~300 строк) — блоки I–XXXVII
- `url-verification.md` (~150 строк) — URL1/URL2/VERIFIED/Карантин
- `document-card.md` (~50 строк) — формат карточки документа
- `fail-safe.md` (~80 строк) — FAIL-SAFE, ANTI-OMIT, АО1–АО3
- `metric-gate.md` (~30 строк) — пороги качества
- `legal-grouping.md` (~40 строк) — критерии объединения подтем

### Принцип оглавления
Пользователь решает об объединении подтем (не агент). Outline-agent только предлагает с обоснованием → пользователь утверждает/корректирует → СТОП.

### Портативность
Три файла обеспечивают запуск с любой машины без перенастройки кода:
1. `config.json` — машинозависимые пути (API ключ, папка выгрузки)
2. `AGENTS.md` — правила (60 строк)
3. `PROJECT_STATE.md` — текущее состояние

### Пороги качества
- Слова: ≥ 8 000
- Знаки: ≥ 122 000
- URL2: ≥ 35 (блокер), цель 50
- Pages (.docx): 70–80 страниц

### Что сохранить в notary_agent.py без изменений
- `fetch_and_log` — протокол работает
- `capture_part_output` — логика capture
- `assemble_subtopic_final` — сборка .md
- `metric_check` — подсчёт метрик
- `build_docx` — генерация .docx
- `validate_part_output` — валидация

### Что добавить в notary_agent.py
- `load_agent(name)` — загружает agents/<name>.md
- `load_skills(names)` — загружает список skills/*.md и склеивает
- `build_context(agent, skills, order, extra)` — собирает контекст для LLM
- `run_hook(event, context)` — вызывает нужный хук

### Команды (CLI)
```
prepare-theme N  → outline-agent
approve-outline N → order-render-agent
run-subtopic N.X → research-agent (Части 2–5)
run-delta N.X → delta-agent (Части 6–9)
assemble N.X → assembly-agent (Части 10–11 + сборка)
publish N.X → quality-agent → PASS → 04-output
next-theme → обновляет PROJECT_STATE.md
```
