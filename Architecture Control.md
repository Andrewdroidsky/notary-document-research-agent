# Architecture Control — Архитектурный контроль LLM-агентов

Универсальное руководство. Написано на основе реального опыта — не теории.
Применимо к любому агенту, независимо от задачи.

---

## Раздел 1. Что такое LLM-агент и почему он ненадёжен по природе

### 1.1 Что такое агент

LLM-агент — это языковая модель (например, Claude, GPT-4, Gemini), которой дали инструменты: читать файлы, писать файлы, искать в интернете, запускать код. Вместо одного ответа в чате — она выполняет цепочку действий.

Агент получает задачу → думает → выбирает инструмент → смотрит результат → думает снова → выбирает следующий инструмент → и так до финала.

Выглядит как автономная работа. Но под капотом это всё та же языковая модель, которая каждый раз "предсказывает следующий токен". Она не "понимает" задачу как человек — она статистически продолжает текст.

### 1.2 Почему агент надёжен на простых задачах и ненадёжен на сложных

**Простая задача:** "переведи этот текст на английский", "найди все файлы с расширением .md", "создай таблицу из этих данных". Один шаг, чёткий результат, легко проверить.

**Сложная задача:** многошаговая, с накопленным контекстом, с требованиями к формату, с верификацией источников, с зависимостями между шагами. Здесь всё ломается.

Три причины — ниже.

---

### 1.3 Причина 1 — Деградация контекста (context decay)

Языковая модель обрабатывает текст в "окне контекста" — это её рабочая память. Всё что туда попало — она видит. Что не попало — не видит вообще.

**Проблема:** окно не бесконечное. Когда разговор (или агентная сессия) становится длинной, самое начало "отодвигается" от текущей позиции. Модель формально его видит, но статистически опирается на него всё меньше — потому что "близкое" перевешивает "далёкое".

**Что происходит на практике:**
- Инструкции из начала промпта выполняются точно → к середине работы — приблизительно → к концу — агент начинает "упрощать", пропускать шаги, менять формат
- Правило "ставить URL2 после каждой карточки" соблюдается в Части 2, нарушается в Части 7
- Формат карточки из эталона воспроизводится в начале, к концу агент начинает "изобретать свой"

**Это не баг и не халтура.** Это физика трансформерной архитектуры. Против неё нет промптов — только машинные ограничители.

---

### 1.4 Причина 2 — Оптимистичное планирование

Агенту легко написать план из 7 пунктов. Исполнить все 7 правильно за один run — намного сложнее.

**Почему так происходит:**
- Генерация плана — один вызов LLM, пара секунд. Никаких последствий если план неточный.
- Исполнение каждого пункта — цепочка действий с потенциальными ошибками, с деградацией контекста, с непредвиденными результатами инструментов.
- Агент не знает заранее где споткнётся. Поэтому он "оптимистично" выдаёт план, а потом на каждом шаге встречает реальность.

**Что вы видите:** агент говорит "сделаю 7 пунктов", делает 3, на 4-м ошибается, на 5-м "не замечает" что 4-й не доделан, к 7-му говорит "готово". Честно верит что готово.

**Решение:** один run — одна атомарная задача. Максимум 2–3 шага. Дальше — проверка, потом следующие шаги.

---

### 1.5 Причина 3 — Defensive copying (копирование "на всякий случай")

Агенты боятся потерять контекст. Поэтому когда им нужно передать информацию на следующий шаг — они копируют всё подряд.

**Как это выглядит:**
- Нужно передать список найденных документов → агент копирует полный текст всех предыдущих ответов
- Нужен промпт для Части 6 → агент вшивает в него мастер-промпт + приказ + interaction guide + примеры выдачи
- Нужна ссылка на файл → агент копирует весь файл целиком

**Результат:** каждый шаг становится дороже (больше токенов), контекст раздувается, деградация начинается раньше.

**Решение:** передавать только то что реально нужно на этом шаге. Всё остальное — ссылка на файл, не копия.

## Раздел 2. Чем нельзя контролировать агента

Это важный раздел. Многие пробуют эти методы и разочаровываются.

### 2.1 Файлы инструкций (CLAUDE.md, AGENTS.md, system prompt)

**Что делают:** текст инструкций подмешивается в промпт при каждом вызове. Агент его видит.

**Почему не работает против дрейфа:** инструкции — это текст. К середине длинной сессии они деградируют вместе со всем остальным. Агент искренне "забывает" что там написано — не потому что игнорирует, а потому что статистически опирается на ближайший контекст.

**Для чего всё равно полезны:** стартовые правила (что делать в начале), общие ориентиры, формат. Как компас — задаёт направление, не управляет каждым шагом.

**Вывод:** инструкции нужны, но не достаточны. Без машинных gates — дрейф неизбежен.

### 2.2 settings.json / конфигурация разрешений

**Что делает:** блокирует конкретные **действия** на уровне кода. "Не запускать rm -rf", "не делать сетевые запросы", "спрашивать перед записью файлов".

**Почему не работает против дрейфа содержания:** settings.json видит действие (запуск команды, запись файла), но не видит содержание (что именно написано в файле, правильный ли формат карточки, есть ли URL2).

**Аналогия:** settings.json — это замок на двери. Он не пускает тех кто не должен войти. Но он не контролирует что происходит внутри комнаты.

**Для чего всё равно полезен:** безопасность (не удалить важные файлы, не уйти за рамки проекта), требование подтверждения перед необратимыми действиями.

### 2.3 Линтер (flake8, ruff, eslint)

**Что делает:** проверяет синтаксис и стиль кода. Находит незакрытые скобки, неиспользуемые переменные, нарушения форматирования.

**Почему не работает против дрейфа:** линтер видит синтаксис, не смысл. Код `return []` синтаксически верен — но если он должен возвращать список ошибок, а возвращает пустой список, линтер это не заметит.

**Для чего всё равно полезен:** быстрая проверка что агент не сломал синтаксис файла. Хорошо ставить как pre-commit hook — тогда сломанный код просто не коммитится.

### 2.4 Аудитор-агент (другой LLM проверяет первый)

**Идея:** пусть один агент проверяет результаты другого.

**Почему не работает:** аудитор — та же языковая модель с теми же проблемами. Он тоже дрейфует, тоже галлюцинирует, тоже говорит "всё хорошо" когда нехорошо. Агент не может надёжно проверять агента.

**Единственное что даёт:** изоляция контекста. Аудитор начинает с чистого окна, не тащит историю проверяемого. Это немного помогает — но не решает проблему содержательного контроля.

**Вывод:** машинный код всегда надёжнее LLM-аудитора.

### 2.5 Обещания агента

Агент говорит "понял, больше не буду", "исправлю", "учёл". Он не врёт — в момент ответа он искренне верит что изменил поведение.

Но обещание — это текст в его ответе. Оно не меняет веса модели, не меняет код, не добавляет проверку. При следующем вызове агент снова работает по той же логике что и раньше.

**Правило:** признание без изменения в коде — ничего не значит. Требуй diff.

## Раздел 3. Что реально работает — пять архитектурных принципов

### Принцип 1 — Минимальный контекст на каждый шаг

**Суть:** каждый LLM-вызов получает ровно столько информации, сколько нужно для этого конкретного шага — и ничего лишнего.

**Из чего исходить при проектировании:**
Спроси себя: "Что LLM должна знать чтобы выполнить именно этот шаг?" Всё остальное — убрать или заменить ссылкой.

**Как реализовать:**
- Каноническим файлам (мастер-промпт, инструкции, руководство) — передавать путь, не содержимое: `[см. /path/to/master-prompt.md]`
- Предыдущим результатам — передавать только ключевые данные (например, список найденных документов), не полный текст
- Примерам выдачи — передавать только при первом шаге, не копировать в каждый последующий вызов

**Как проверить что сделано правильно:**
Замерь размер входного пакета для каждого шага в байтах. Если пакет для шага 7 весит в 3 раза больше пакета для шага 2 — что-то накапливается лишнее.

**Guard в коде:**
```python
# Если канонический файл обнаружен телом в пакете — ошибка
def guard_no_canonical_inline(payload: str, canonical_texts: dict) -> None:
    for path, text in canonical_texts.items():
        if text and text in payload:
            raise ValueError(f"Canonical file must not be inlined: {path}")
```

### Принцип 2 — Single source of truth (одно место для каждого факта)

**Суть:** любое состояние системы — что сделано, что следующее, какой порядок, какие настройки — хранится в одном файле. Агент читает оттуда, пишет туда. Не держит в голове.

**Почему это важно:**
Если агент "помнит" что следующая подтема — X, а в файле написано Y — агент ошибётся. У него нет надёжной памяти между вызовами. Файл — есть.

**Из чего исходить при проектировании:**
Для каждого куска состояния спроси: "Где это хранится? Если агент перезапустится — он восстановит это из файла или потеряет?"

Типичные куски состояния:
- Текущая задача (что делаем сейчас)
- Порядок шагов (что после чего)
- Что уже сделано (статус каждого шага)
- Пороги и настройки (минимальные метрики, режимы работы)

**Как реализовать:**
```python
# Плохо: агент держит порядок в голове
next_subtopic = "16.8.2"  # откуда он это знает?

# Хорошо: агент читает порядок из файла
def get_next_subtopic(outline_file, current_id):
    entries = parse_outline(outline_file)
    current_idx = next(i for i, e in enumerate(entries) if e.id == current_id)
    return entries[current_idx + 1] if current_idx + 1 < len(entries) else None
```

**Как проверить:**
Убери агента из сессии и верни. Может ли он восстановить полное состояние только из файлов — без истории чата? Если да — всё правильно.

### Принцип 3 — Gates перед необратимыми действиями

**Суть:** перед каждым действием которое нельзя легко отменить — автоматическая проверка в коде. Если проверка не прошла — действие заблокировано. Агент не может это обойти.

**Что такое необратимое действие:**
- Публикация финального файла (потом клиент увидит)
- Коммит в git (история меняется)
- Отправка письма / сообщения (уже доставлено)
- Обновление статуса задачи как "завершена" (другие на это опираются)
- Запись результата в БД / хранилище

**Из чего исходить при проектировании:**
Пройди весь workflow и выпиши все точки где агент что-то "финализирует". Каждая такая точка — кандидат на gate.

**Как реализовать gate:**

Шаг 1: Определи критерии прохождения (числовые, не субъективные):
```python
PUBLISH_MIN_WORDS = 16000
PUBLISH_MIN_URL1 = 100
PUBLISH_MIN_URL2 = 100
```

Шаг 2: Реализуй проверку перед действием:
```python
def enforce_publish_gate(metrics: dict) -> None:
    shortfalls = []
    if metrics["words"] < PUBLISH_MIN_WORDS:
        shortfalls.append(f"слов: {metrics['words']} < {PUBLISH_MIN_WORDS}")
    if metrics["url1"] < PUBLISH_MIN_URL1:
        shortfalls.append(f"URL1: {metrics['url1']} < {PUBLISH_MIN_URL1}")
    if shortfalls:
        raise RuntimeError(f"Gate не пройден: {'; '.join(shortfalls)}")
```

Шаг 3: Выводи метрики до попытки действия — чтобы видеть сколько не хватает:
```json
{
  "publish_ready": false,
  "words": 14230,
  "words_required": 16000,
  "shortfall_words": 1770
}
```

**Важно:** gate — это код, не текст в промпте. Агент физически не может опубликовать файл пока gate не пройден.

### Принцип 4 — Валидация отдельно от генерации

**Суть:** каждая функция которая принимает вывод LLM — имеет парную функцию которая этот вывод проверяет. Если валидация не прошла — вывод не принимается, агент обязан переделать.

**Почему отдельно:** валидатор пишется один раз, проверяет всегда. Агент может дрейфовать в 10-й раз — валидатор поймает так же как и в 1-й.

**Из чего исходить при разработке валидатора:**

Шаг 1: Возьми эталонный готовый результат (который точно правильный).

Шаг 2: Выпиши всё что в нём обязательно присутствует — структурно, не по содержанию:
- Какие заголовки и в каком порядке?
- Какие поля в каждой карточке?
- Что обязательно должно быть рядом с чем?
- Что никогда не должно появляться?

Шаг 3: Каждый пункт списка — одна проверка в коде.

Шаг 4: Пороги (минимальное количество символов, строк, элементов) — измерь по реальным готовым файлам, не придумывай.

**Пример логики валидатора:**
```python
def validate_output(text: str, step_number: int) -> list[str]:
    issues = []

    # Структура
    if "ОБЯЗАТЕЛЬНЫЙ ЗАГОЛОВОК" not in text:
        issues.append("Отсутствует обязательный заголовок")

    # Карточки документов
    cards = find_document_cards(text)
    for i, card in enumerate(cards):
        if "URL2:" not in card:
            issues.append(f"Карточка {i+1}: отсутствует URL2")
        if "Полное наименование:" not in card:
            issues.append(f"Карточка {i+1}: отсутствует полное наименование")

    # Объём
    if len(text) < MIN_CHARS_PER_STEP:
        issues.append(f"Объём {len(text)} символов, минимум {MIN_CHARS_PER_STEP}")

    return issues  # пустой список = ОК
```

**Правило:** функция без парного валидатора считается незавершённой.

### Принцип 5 — Атомарные задачи с проверкой между ними

**Суть:** один агентный run — одна чёткая задача с понятным критерием завершения. После — проверка (автоматическая или визуальная). Потом следующий run.

**Из чего исходить при декомпозиции задачи:**

Хорошая атомарная задача:
- Имеет один чёткий результат ("захвачена Часть 2 с validation_passed: true")
- Результат можно проверить автоматически или за 30 секунд вручную
- Если что-то пошло не так — понятно на каком шаге

Плохая задача:
- "Сделай всё" — нет критерия
- "7 пунктов за один run" — слишком длинно, дрейф неизбежен
- "Постарайся не ошибиться" — не задача, пожелание

**Практическое правило:** если задача требует больше 3 инструментальных вызовов — скорее всего её надо разбить.

**Diff-протокол (для задач на изменение кода):**

Любое изменение кода проходит через:
1. Агент делает изменение
2. Агент показывает `git diff` только изменённых функций
3. Проверяешь diff ДО запуска (30 секунд)
4. Только после подтверждения — запуск

Почему до, а не после: если запустить с неправильным кодом — токены и время сгорели. Diff до — ничего не стоит.

## Раздел 4. Типичные ошибки при построении агента

### 4.1 "Положу все файлы рядом — LLM сама разберётся"

Агент создаёт папку `00-context` и копирует туда всё: мастер-промпт, руководство, примеры, историю, Приказ. Логика: "пусть видит всё".

**Что происходит:** контекст раздувается до 1.5–2 MB. Деградация начинается после первых 2–3 шагов. Стоимость растёт в разы.

**Правило:** LLM должна получать не "всё", а "нужное для этого шага". Остальное — ссылки на файлы.

### 4.2 "Добавлю правило в инструкции — он перестанет нарушать"

AGENTS.md вырастает до 300+ строк. Каждое новое нарушение — новое правило. Агент читает, соглашается, нарушает снова.

**Что происходит:** AGENTS.md сам становится частью раздутого контекста. Правила в нём — тот же текст который деградирует.

**Правило:** каждое правило поведения которое нарушается повторно — должно быть реализовано как gate или валидатор в коде, не как текст в промпте.

### 4.3 "Функция написана — значит работает"

Агент пишет функцию `update_project_state()` — но нигде её не вызывает. Говорит "готово". Искренне считает что реализовал.

**Правило:** после любого diff — проверить что новая функция вызывается в боевом пути. Мёртвый код не считается реализацией.

### 4.4 "Валидатор есть — значит всё проверяется"

Валидатор написан для шагов 1–5 и 10–11. Шаги 6–9 — без покрытия. Дрейф происходит именно там — и проходит незамеченным.

**Правило:** каждый шаг который принимает вывод LLM — имеет проверку. Даже если "там и так понятно". Особенно там.

### 4.5 Regex написан неверно и всегда возвращает 0

```python
# Это считает только пустые строки URL2: (без значения после двоеточия)
re.findall(r"(?m)^\s*URL2:\s*$", text)

# Это считает правильно
re.findall(r"(?m)^\s*URL2:\s*.+", text)
```

Первый вариант всегда возвращает 0 — валидатор всегда FAIL даже когда ссылки есть. Агент не может пройти gate. Работа стоит.

**Правило:** регулярные выражения проверять на реальных примерах из готовых файлов — не на абстрактных тестах.

### 4.6 Пороги взяты произвольно

"Минимум 200 символов на шаг" — откуда 200? Если реальный минимум в готовых файлах — 1789 символов, порог 200 не поймает пустой шаг.

**Правило:** пороги всегда измерять по реальным готовым результатам. Взять минимум из всех готовых файлов, поставить порог чуть ниже (15–20%) чтобы не было ложных срабатываний — но пустые шаги всё равно ловились.

## Раздел 5. Структура надёжного агента — что строить и в каком порядке

### 5.1 Что строить (компоненты)

**Компонент 1 — Хранилище состояния**
Файл (или несколько файлов) где хранится: текущий шаг, что сделано, порядок задач, настройки. Агент читает оттуда при каждом запуске.

**Компонент 2 — Пакетизатор (context builder)**
Код который собирает входной пакет для каждого LLM-вызова. Только нужное, никакого инлайна канонических файлов. Guards внутри.

**Компонент 3 — Валидатор**
Парные функции для каждого шага. Принимает вывод LLM, возвращает список проблем или пустой список.

**Компонент 4 — Gates**
Проверки перед необратимыми действиями. Блокируют если условие не выполнено. Выводят конкретные цифры (что не хватает и сколько).

**Компонент 5 — Журнал (manifest)**
Файл где фиксируется статус каждого шага: захвачен / validation_passed / ошибка. Позволяет восстановить работу после перерыва.

**Компонент 6 — Навигатор порядка**
Функция которая определяет следующий шаг из файла с планом — не из памяти агента. Вызывается автоматически при завершении шага.

### 5.2 В каком порядке строить

```
1. Определить формат результата (эталонный файл)
       ↓
2. Определить метрики качества (числовые пороги)
       ↓
3. Написать валидаторы (из эталона и метрик)
       ↓
4. Написать gates (из метрик)
       ↓
5. Спроектировать хранилище состояния
       ↓
6. Написать навигатор порядка
       ↓
7. Написать пакетизатор (минимальный контекст)
       ↓
8. Написать журнал
       ↓
9. Соединить всё в workflow
       ↓
10. Проверить на граничных случаях
```

**Почему такой порядок:** начинаем с результата и критериев — они не меняются. Валидаторы и gates строятся из критериев. Остальное — инфраструктура вокруг них.

Если начать с инфраструктуры (workspace, пакеты, команды) — велик риск что к концу окажется что непонятно что считать правильным результатом.

### 5.3 Схема взаимодействия

```
Пользователь
    │ команда
    ▼
Оркестратор (CLI / агент)
    │
    ├─→ Навигатор порядка ─→ Хранилище состояния
    │
    ├─→ Пакетизатор ──────→ LLM-вызов
    │                            │
    │                            ▼ вывод LLM
    ├─→ Валидатор ◄──────────────┘
    │       │ ОК / FAIL
    │       ▼
    ├─→ Журнал (фиксирует статус)
    │
    └─→ Gate ──────────────→ Публикация (только если Gate пройден)
```

## Раздел 6. Экономика токенов

### 6.1 Откуда берётся стоимость

Токены = входящий контекст + выходящий ответ. Входящий контекст — главный драйвер стоимости.

**Из чего состоит входящий контекст на один LLM-вызов:**
- Системный промпт / инструкции
- Канонические файлы (если инлайнятся)
- История предыдущих шагов (если кумулятивная)
- Текущее задание
- Примеры / эталоны (если передаются)

**Где обычно скрывается лишнее:**
- Дублирование: один и тот же файл в двух местах (в execution packet и в `00-context` отдельно)
- Кумулятивные пакеты: каждый следующий шаг тащит полный текст всех предыдущих
- Инлайн больших файлов: мастер-промпт (74 KB), руководство (451 KB) — в каждый вызов

### 6.2 Что можно резать без потери качества

| Что убрать | Почему безопасно |
|-----------|-----------------|
| Дублирующиеся копии одного файла | Агент видит файл один раз — достаточно |
| Полный текст предыдущих шагов в follow-up | Достаточно списка ключевых данных (названия документов) |
| Инлайн инструкций в каждый пакет | Заменить ссылкой — агент читает файл сам |
| Файлы не относящиеся к текущему шагу | Если шаг 7 не использует файл X — зачем ему его видеть |

### 6.3 Что нельзя резать

**Нельзя резать ради экономии:**
- Содержание шагов (карточки документов, аналитические блоки)
- URL ссылки в карточках
- Список уже найденных документов для follow-up (нужен для дедупликации)
- Инструкции специфичные для текущего шага

**Правило:** экономия за счёт содержательного слоя — запрещена. Экономить можно только на служебном слое (дублирование, инлайн, кумуляция).

### 6.4 Как измерить эффект оптимизации

До изменения: замерить размер входного пакета для каждого шага в байтах.
После изменения: замерить снова.
Сравнить.

Если агент считает токены — смотреть отчёт после каждого прогона. Если нет — можно приближённо считать: 1 токен ≈ 4 символа на русском тексте, ≈ 3.5 символа на английском.

## Раздел 7. Как проверять работу агента — практические приёмы

### 7.1 Три уровня проверки

**Уровень 1 — Автоматический (машинный)**
Валидаторы и gates срабатывают без участия человека. Агент не может пройти дальше если проверка не пройдена.

**Уровень 2 — Промежуточный (30 секунд)**
После ключевого шага — быстрый взгляд на первые 20–30 строк результата. Соответствует ли эталону? Если нет — стоп, переделка сейчас пока не сгорели токены на следующие шаги.

**Уровень 3 — Финальный (до публикации)**
Pre-publish JSON с метриками. Принять решение: публиковать как есть или дать команду на добор.

### 7.2 Что смотреть в diff

Когда агент показывает diff (разницу в коде) — проверяй:

- Изменена именно та функция которую просили?
- Нет ли удалённых веток/режимов которые должны были остаться?
- Новая функция вызывается в боевом пути — не просто объявлена?
- Regex корректен для реальных данных?
- Синтаксис проверен (`py_compile` или аналог)?

### 7.3 Типичные баги в коде агента

| Симптом | Реальная причина |
|---------|-----------------|
| Gate всегда FAIL даже когда данные правильные | Regex `\s*$` вместо `\s*.+` — считает только пустые строки |
| Режим сломан, всегда падает с ошибкой | Агент удалил ветку кода вместо того чтобы добавить guard |
| Функция написана но ничего не меняется | Функция объявлена, но нигде не вызывается (мёртвый код) |
| Guard всегда срабатывает | Агент вернул инлайн в ту же ветку где стоит guard — guard ловит то что сам же вставил |
| Кириллица в файле испорчена | Программная замена строк без явного `encoding='utf-8'` |

## Раздел 8. Контрольный список при построении нового агента

### До начала

- [ ] Определён единственный результат агента (что именно на выходе)
- [ ] Есть эталонный пример правильного результата
- [ ] Определены числовые метрики качества (не "хорошо", а "≥ 16 000 слов")
- [ ] Определены все точки где агент делает необратимые действия

### При проектировании

- [ ] Каждый LLM-вызов получает только нужный контекст (не "всё")
- [ ] Нет дублирования одних и тех же данных в разных местах
- [ ] Состояние хранится в файлах, не в памяти агента
- [ ] Порядок шагов читается из файла, не из головы агента
- [ ] Для каждого шага с выводом LLM — парный валидатор
- [ ] Gate перед каждым необратимым действием
- [ ] Журнал фиксирует статус каждого шага

### При разработке валидаторов

- [ ] Пороги взяты из реальных готовых файлов, не придуманы
- [ ] Regex проверен на реальных примерах
- [ ] Каждый валидатор вызывается в боевом пути (не мёртвый код)
- [ ] Валидатор возвращает конкретный список проблем, не просто True/False

### При изменении кода

- [ ] Diff показан до запуска прогона, не после
- [ ] Одна задача — один diff (не смешивать несвязанные изменения)
- [ ] Синтаксис проверен после каждого изменения
- [ ] Новые функции вызываются в боевом пути

### При запуске

- [ ] Первый прогон — на небольшой тестовой задаче
- [ ] Проверить граничные случаи: пустой ввод, shortfall, нарушение формата
- [ ] Убедиться что gate реально блокирует (а не просто выводит предупреждение)

## Словарь терминов

| Термин | Значение |
|--------|----------|
| **Gate** | Точка проверки — пропускает дальше только если условие выполнено; реализована в коде |
| **Guard** | Проверка инварианта с ранним выходом (`raise ValueError`) внутри функции |
| **Single source of truth** | Один файл/место для каждого факта; всё остальное только читает оттуда |
| **Атомарная задача** | Задача с одним чётким результатом, который можно проверить автоматически |
| **Context decay** | Деградация точности LLM по мере удаления инструкций от текущей позиции в контексте |
| **Defensive copying** | Копирование всего "на всякий случай" — типичная причина раздутых пакетов |
| **Diff** | Разница между старой и новой версией файла — инструмент проверки изменений в коде |
| **Мёртвый код** | Функция объявлена, но нигде не вызывается — не влияет на поведение |
| **Линтер** | Проверка синтаксиса и стиля кода без запуска (flake8, ruff, eslint) |
| **Manifest** | Журнал статусов шагов текущего прогона |
| **Shortfall** | Недобор до порогового значения (например, нужно 16 000 слов, есть 14 000) |
| **Инлайн** | Вставка полного содержимого файла в тело пакета (вместо ссылки на файл) |
| **Кумулятивный контекст** | Когда каждый следующий шаг содержит полный текст всех предыдущих |
| **CI/CD** | Continuous Integration/Delivery — автоматическая проверка и доставка; аналог: gate + publish |
| **Pre-commit hook** | Скрипт который запускается автоматически перед каждым коммитом в git |
