## ЧАСТЬ 4. Диагноз: почему высокий расход токенов

### Главная находка — 00-context копирует 1.9 MB канона в каждый run

При каждом старте подтемы агент создаёт папку `00-context` и физически копирует туда все канонические файлы:

| Файл | Размер |
|------|--------|
| `07-execution-packet.md` | 583 KB |
| `08-interaction-guide.md` | 451 KB (полная копия User and LLM Interaction guide) |
| `09-output-example.md` | 414 KB (полный пример готового результата) |
| `03-master-prompt.md` | 74 KB |
| `00-agents.md` | 58 KB |
| `01-project-state.md` | 40 KB |
| **Итого `00-context`** | **~1.9 MB на каждый run** |

### Execution packet содержит три документа целиком внутри себя

Функция `build_execution_packet()` (строки 1218–1255) буквально склеивает в один файл:
- полный текст мастер-промпта
- полный текст Приказа (со всеми 11 Частями в развёрнутом виде)
- полный текст interaction guide

Это причина того, что execution packet весит 583 KB при исходном шаблоне Приказа 49 KB.

### Двойное дублирование

После этого функция `write_subtopic_run_files()` (строки 4772–4790) копирует в `00-context`:
- `03-master-prompt.md` — отдельно
- `07-execution-packet.md` — который уже содержит мастер-промпт внутри
- `08-interaction-guide.md` — отдельно
- `07-execution-packet.md` — который уже содержит interaction guide внутри

Мастер-промпт и interaction guide присутствуют в `00-context` дважды: один раз сами по себе, второй раз внутри execution packet.

### Follow-up пакеты кумулятивные по дизайну

Функция `build_literal_context_bundle()` (строки 1906–1930) для каждого пакета Части N загружает полные тексты Частей 1 через N-1:

| Пакет | Что тащит внутрь | Примерный объём |
|-------|-----------------|-----------------|
| Часть 6 | Части 1–5 | ~160 KB |
| Часть 7 | Части 1–6 | ~170 KB |
| Часть 8 | Части 1–7 | ~178 KB |
| Часть 9 | Части 1–8 | ~186 KB |
| Часть 10 | Части 1–9 | ~195 KB |
| Часть 11 | Части 1–10 | ~210 KB |
| **Итого по 6 пакетам** | | **~1.1 MB** |

### Правило 2% физически нереализуемо

Если substantive output на одну подтему ~200 KB (~50–100K токенов), а только `00-context` загружает ~1.9 MB (~400–500K токенов), то orchestration overhead структурно больше 100% от substantive-слоя, а не 2%. Это не вина агента — это математика текущего дизайна воркспейса.

### Почему диалог о дисциплине ничего не решил

В диалоге с Кодекс-агентом лечилось поведение (сколько раз писать в чат, останавливаться ли). Но расход токенов идёт не от чат-сообщений, а от загрузки контекста: 1.9 MB в `00-context` + кумулятивные follow-up пакеты. Это структурная проблема, не поведенческая. Добавление правил в AGENTS.md одновременно:
- не лечит причину
- увеличивает файл, который сам является частью проблемы

### Почему агент так построил систему

Агент сделал это из избыточной предосторожности (defensive copying): "скопирую всё рядом, чтобы LLM видела весь контекст". Каждое отдельное решение выглядело разумным. Никто не делал шаг назад и не спрашивал "а сколько это весит суммарно". Агент не умеет сам замечать что система целиком деградирует — он видит только текущую задачу.

## ЧАСТЬ 11. Почему при ручном вводе не было такого расхода

**Пользователь:** А почему при ручном вводе не было такого расхода? Или я не замечал?

**Claude:**

Скорее всего не замечал — по нескольким причинам:

1. **При ручном режиме пользователь был посредником.** Он сам копировал нужный кусок промпта в окно LLM, получал ответ, копировал следующий кусок. Каждый шаг был отдельным коротким сообщением. LLM не держала весь контекст — пользователь сам управлял тем что в неё входит.

2. **Агент делает это автоматически — но одним куском.** Он собирает всё в один пакет и отправляет целиком. Это удобнее для пользователя, но дороже в токенах.

3. **Токены в ручном режиме тоже тратились** — просто были распределены по многим коротким сессиям, и общую сумму никто не суммировал. Пользователь видел каждый отдельный запрос, а не итог по теме.

4. **Агент добавил своё сверху** — 00-context, execution packet, follow-up пакеты. Этого в ручном режиме вообще не было.

Если бы суммировать все токены ручного режима по одной теме — цифра была бы сопоставимой или даже больше, потому что пользователь наверняка возвращался, переспрашивал, уточнял. Агент хотя бы делает это за один проход.
